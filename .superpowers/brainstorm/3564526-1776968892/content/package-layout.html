Monorepo package layout after the split

All three options use gRPC+Protobuf, shared MongoDB+GridFS, mTLS, and the cmd-hub/cmd-node naming. They differ only in where code lives.

A

Split cmd-hub into three packages recommended

packages/
  cmd-hub-core/        shared types, BaseCommandService, ConfigRegistry,
                       message-lifecycle, UI interfaces, protobuf-generated code
  cmd-hub/             the gateway process:
                       UI host, CmdDispatcher (now routing),
                       CmdNodeRegistry, gRPC server, FileService (GridFS)
  cmd-node/            the node runtime:
                       gRPC client, manifest builder, metrics collector,
                       command/service host (reuses BaseCommandService)
  cmd-node-system/     a cmd-node that exposes built-ins (/help /config
                       /sconfig /node); bundled as its own Docker image
  org-scraper/         unchanged public API, now consumed by a cmd-node
  app/                 the deployable. Composes: cmd-hub + telegram UI
                       plugin. Runs docker-compose with cmd-node-system
                       and org-scraper's cmd-node.

Pros

  • One package = one role. Easy to reason about.
  • cmd-hub-core is importable by both sides without pulling server code into nodes or client code into gateway
  • Each image has a minimal dep graph → smaller Docker images
  • Plugin authors depend on cmd-node (small) not cmd-hub (heavy)

Cons

  • Five packages instead of three. More tsconfig wiring up front
  • Moving BaseCommandService to cmd-hub-core touches many files
B

Keep cmd-hub monolithic; add cmd-node sibling

packages/
  cmd-hub/             BOTH the gateway and the shared core:
                       UI interfaces, BaseCommandService, ConfigRegistry,
                       CmdDispatcher, CmdNodeRegistry, gRPC server.
                       Nodes import from here too.
  cmd-node/            gRPC client, manifest, metrics. Imports cmd-hub
                       for types/BaseCommandService.
  org-scraper/         same
  app/                 same

Pros

  • Fewer packages, less tsconfig work
  • No big file moves in cmd-hub

Cons

  • cmd-node transitively pulls in gateway-only code (UI, Telegraf, Mongo, gRPC server) → bloated node image
  • Fuzzy boundary: anyone editing cmd-hub has to know "does this run on the gateway, the node, or both?"
  • Plugins like org-scraper depend on the whole cmd-hub
C

One package, two entry points

packages/
  cmd-hub/             everything. Two bins:
                         cmd-hub-gateway  (starts the hub)
                         cmd-hub-node     (starts a node)
                       Conditional imports / subpath exports.
  org-scraper/         same
  app/                 same

Pros

  • Minimum ceremony

Cons

  • npm publishes one artifact for two very different runtimes
  • Tree-shaking won't save Docker images: install pulls everything
  • Hard to spot when server-only code leaks into the node runtime
  • Dishonest boundary — everyone has to read imports to know what runs where
